# PNT-036 — gate G1: the driver path in the browser against the real API

`apps/web/e2e/live/g1.live.spec.ts` runs the G1 path of 16 / 17 TC-057 at 390 px against the real API (S2 use-cases,
`apps/api` built to dist) on a freshly migrated and seeded PostgreSQL 16, then checks the database in SQL. It is a
separate Playwright project (`g1-live`), added only with `E2E_BACKEND=live`, so the mocked suite stays fast and needs
no database.

```bash
pnpm --filter @point/web test:e2e:live   # builds shared/db/server/api (tsc, ~4 s), then the g1-live project
# TEST_DATABASE_URL = a PostgreSQL 16 where we may CREATE DATABASE (default postgres://postgres:postgres@localhost:5432/postgres)
# E2E_API_PORT (default 3917) = the API port the vite preview proxies /v1 to
```

## How the run is wired

- **API.** `e2e/live/api-server.mjs` (test code, never deployed) creates a throwaway database on `TEST_DATABASE_URL`,
  applies the migrations (the first is `docs/06_schema.sql`), loads the docs/17 §4 seed like `apps/api/test/harness.ts`
  (supervisor MFA requirement off, as the API tests do), and starts `createApp` from `apps/api/dist` with
  `APP_BASE_URL` = the web origin, so the CSRF Origin check passes through the proxy. SIGTERM closes the app and
  drops the database. A worker-scoped fixture (`e2e/live/fixtures.ts`) spawns it and gives the spec SQL access.
- **Same origin.** The browser loads the production build from `vite preview`, which proxies `/v1` to
  `localhost:API_PORT` (vite.config.ts now reads `API_PORT`; the e2e web server gets `E2E_API_PORT`). Session cookies,
  `Origin`, CSRF and Idempotency-Key are therefore exactly the production path. One worker: one API port.
- **Sign-in.** DRV1 and DRV2 sign in through D-01 with their development-seed PINs; SUP-R signs in with
  `POST /v1/auth/login` on a Playwright request context and requests the car on behalf (`liveSignIn` / `liveExec` in
  `e2e/support/backend.ts`; TOTP for OWN1/ADM1 in `e2e/support/totp.ts`, unit-tested with the RFC 6238 vectors).
- **Photos.** Without S3 the API uses its in-memory private bucket, whose presigned URLs point at
  `http://object-storage.invalid/…`. The page routes those requests to the API process (`/__e2e/storage`, test-only,
  added by the launcher), where the bucket checks the signature, expiry, Content-Type and exact length itself; the
  route answers the CORS preflight and adds `Access-Control-Allow-Origin` like a bucket configured for the web
  origin. The app's photos are real JPEGs, so the API's sanitizer (sharp) runs on them at `complete`.
- **Command contract.** `BrowserCommandLog` (`e2e/support/commandLog.ts`) records every `/v1` request of a page in the
  browser and lets it through unchanged (`route.continue()`), with a per-route hold, so `pressCommand` proves the same
  contract as on the fake: one request per press with a UUIDv4 key and the CSRF header, the button disabled and busy
  until the reply, the reply's status.

## Checked against the S2 handlers

Request bodies (strict zod schemas), replies and views of `packages/server/src/use-cases/**` match what the screens
send and read on the whole G1 path — the live run passed first time. Differences found and aligned in the web app or
the fake: `GET /v1/me/home` lists `open` and `closing` events (D-03/D-04 offer only `open` ones for an intake); the
handover checks the payment gate before the verification and counts wrong paper stubs against
`handover.max_attempts` (`PAPER_STUB_MISMATCH {attempts_left}`, then `HANDOVER_CODE_LOCKED`, now shown under the
stub field with the field and the button disabled); a payment on a ticket that is not due is `VALIDATION_FAILED`;
the retrieval assignee does not see `paper_serial`, the fee is for staff and the retrieval assignee; `PLATE_INVALID`
carries `field`/`reason`; serials and tags are normalized (upper case, Latin digits).

## Proposed decisions and notes (numbering left to the lead)

**A — The live G1 project in CI.** Added to the existing `e2e` job (one more Postgres service and one step) rather than a
new job, to save minutes; the mocked run is unchanged. The root `package.json` and CLAUDE.md §7 do not list
`test:e2e:live` yet.

**B — Browser uploads to a real bucket.** The e2e route stands in for a bucket CORS rule. Staging/production need the
media bucket to allow `PUT` (and `GET`) from the web origin with the `Content-Type` header (05, PNT-027 deployment
notes); a missing rule shows as `MEDIA_UPLOAD_INCOMPLETE` on the tile.

**C — `safety_note_ar`.** `GET /v1/me/home` sends «احجز فقط وأنت متوقف؛ لا تستخدم الجوال أثناء القيادة» for a
reserve-next card, while 02 D-09 / 03 §3 fix the note «احجزه فقط وأنت متوقف. لا تستخدم الجوال أثناء القيادة.»;
the card shows the 02 text. Proposed: align the server text with 02 or drop the field.

**D — Collection at handover.** Until PNT-080 the API answers `PAYMENT_PENDING` for a due ticket even with a payment in
the body, so the D-11 collection (per-vehicle events) completes only on the fake, which already models the inline
collection of 13. G1 runs on the included event.

**E — Paper lock UI.** 08 gives `HANDOVER_CODE_LOCKED` a blocking dialog «اتصل بالمشرف»; D-11 shows the 08 text under
the stub field and disables the field and the button (the code variant has the CodeInput locked state). A dialog
can follow with the supervisor exception flow (`handover-exception`).
