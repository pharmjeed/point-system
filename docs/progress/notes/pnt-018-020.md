# PNT-018 … PNT-020 — المواقع والإعدادات والتخطيط، دورة حياة الحفل، الورديات (notes)

Module `packages/server/src/modules/venues-events/` (domain → infra → application → http), mounted through
`VenuesEventsHttpModule` in `apps/api/src/features.ts`. It serves the 29 routes of canon §9.5 except
`start-closing`, `close`, `reconciliation` and `operations` (S6–S7). No change to the core and none to
`pg-constraint-map.ts`: every constraint these commands can hit (`venues_org_id_code_key`,
`parking_zones_venue_id_name_key`, `parking_spots_zone_id_label_key`, `key_boards_venue_id_name_key`,
`key_slots_key_board_id_label_key`, `dispatch_pools_venue_id_name_key`, `uq_dispatch_pools_default`,
`uq_shifts_open_per_pool`) was already mapped.

`ASSIGNMENT_REQUIRED`); an id-addressed row outside the scope or in another organization is `404
RESOURCE_NOT_FOUND` with `resource` (DEC-PROPOSED-4). Drivers read only the layout of their active-assignment venue,
active items only, with `occupied` (DEC-33, PNT-018 AC4).

## For other modules (exported from `@point/server`)

```ts
VenuesEventsHttpModule
venueSettingsFor(q, venueId): Promise<VenueSettings>      // effective settings (canon §12 defaults); 404 venue if missing
findDefaultDispatchPool(q, venueId): Promise<{ id; venue_id; status } | null>
findOpenShiftForPool(q, poolId): Promise<{ id; venue_id; dispatch_pool_id; version } | null>
listVenueEventsByStatus(q, venueId, statuses = ['open']): Promise<VenueOpenEvent[]>   // newest first
type VenueOpenEvent = { id; name_ar; status; dispatch_pool_id; event_date }           // event_date 'YYYY-MM-DD'
```

`q` is a `Tx` or the `Database`. None of them locks and none caches: read inside the command's transaction, after
its own locks when the value must be stable. The Nest module also exports its five services for in-process use.

Contracts the next tickets rely on:

1. **Intake (PNT-025):** L1 pool → L2 event `FOR NO KEY UPDATE`, then `status = 'open'` (else `EVENT_NOT_OPEN`).
   Event open/PATCH/cancel hold L2, so intake and cancel serialize; a cancel never races a new ticket.
2. **Duty start (PNT-024):** lock L1 of the pool first, then read the open shift (`findOpenShiftForPool(tx, …)`,
   else `SHIFT_NOT_OPEN`). Shift close holds the same L1 while it ends the sessions, so a duty start cannot attach to
   a shift that is being closed.
3. **complete-parking, release-custody to a slot, custody transfer to a slot (S2/S3):** after the canon locks, read
   the spot with its zone (the slot with its board) `FOR SHARE` and require both `active`, then insert the allocation
   (`uq_spot_alloc_spot_active` → `PARKING_SPOT_OCCUPIED`, `uq_key_alloc_slot_active` → `KEY_SLOT_OCCUPIED`). The
   explicit `FOR SHARE` matters: the foreign key alone takes `FOR KEY SHARE`, which does not conflict with the
   `FOR NO KEY UPDATE` that PATCH parking-spots/key-slots takes before its occupancy check, so without it a
   deactivation and an allocation could both commit.
4. **Pick lists (D-08):** `GET …/parking-spots?available_only=true`, `…?active_only=true` on zones, spots and boards
   (always on for drivers).

## DriverReleaseHook — how shift close uses the core seam

`POST /v1/shifts/{shiftId}/close` calls `releaseDriverWork(tx, { orgId, driverId, poolId: <the shift's pool>,
reason: 'shift_closed', actorId: <closing user> })` once per auto-ended session, in ascending `duty_session_id`
order, inside the close transaction:

- At the call: L1 of the shift's pool is held (`tx.locks.holdsDispatchPool`); the shift row is already `closed`; the
  open sessions of the shift are locked (L8); this driver's session is still open; sessions of the drivers handled
  before him are already `ended`. He holds no vehicle or key and has no task that is not `completed`/`canceled`
  (otherwise the close was refused), so only his live offers remain to revoke.
- The hook must not end or change the duty session: venues-events ends it right after the call
  (`UPDATE … WHERE status <> 'ended' RETURNING` through `tx.one`, which fails loudly if the hook ended it), then emits
  `driver.duty_ended` and `driver.availability_changed` (`off_duty`).
- The hook locks L4–L7 after the L8 rows: allowed by the canon §14ب L1 exception (`LockTracker`). Every other writer
  of those rows for the same pool must take that pool's L1 first, or L7/L8 could deadlock.
- For the dispatch module (seen in its branch): the pass runs with `excludeUserIds: [driverId]`, so while driver k
  is released it may offer queued work to drivers k+1… of the same closing shift; their own call revokes it a moment
  later in the same transaction. The final state is right, but `task.offered`/`task.offer_revoked` pairs reach the
  outbox. Suggestion: the pass skips sessions whose shift is not `open` (the shift row is `closed` before the first
  call).
- `apps/api/test/shifts-lifecycle.int.test.ts` registers a recording hook (asserting `holdsPool` and
  `dutyStillOpen`), which replaces the dispatch hook in that test file only. Once dispatch is merged, add an
  end-to-end close test with the real hook (a live single offer revoked, no offer left to an ended driver).

## Locks

- Canon §14ب: pools L1 (`lockPools`; PATCH dispatch-pools locks all pools of the venue, shift open/close the shift's
  pool), events L2 (`lockEvents`), duty sessions L8 (`lockDutySessions`, shift close).
- Rows outside §14ب (`venues`, `parking_zones`, `parking_spots`, `key_slots`, `shifts`) are locked
  `FOR NO KEY UPDATE` alone in their own setup command, or (shifts) right after their pool's L1 (DEC-PROPOSED-13).
- An id-addressed command reads the row's org/venue without a lock first, so a row of another venue or organization is
  never locked; after the locks it re-checks the scope against `role_scopes` (TOCTOU).

## Spec gaps left open (implemented as described, no decision taken)

- **Venue deactivation** (`PATCH /v1/venues/{venueId}` `status: inactive`) has no guard in the spec; it is accepted even
  with open events, open shifts or open tickets. Suggest refusing with an open/closing event or an open shift.
- **Zone/board deactivation** with occupied spots/slots is accepted (07 guards spots and slots only); the occupied
  items vanish from pick lists but stay allocated. Suggest the same guard as spots (`PARKING_SPOT_OCCUPIED` with the list).
- **Pool deactivation** checks open tasks and an open shift (07 §2.5) but not draft/open events on the pool, which
  then cannot open (`dispatch_pool_inactive`).
- **Canceling an open event** emits no domain event (canon §7.1), so screens learn it only on their next fetch;
  suggest `event.canceled` or `sync.required` (`scope = events`).
- **Audit redaction** (`core/logging/redact.ts`) masks every key that contains `code`, so `handover.code_ttl_min`
  appears as `[REDACTED]` in the settings before/after of the audit row; suggest matching whole sensitive key names
  (plus the existing safe list) instead of substrings.
- `07_openapi.yaml` `openEvent` says «الشروط: status=draft» although canon §5 and 11 §6.4 allow closing → open.
