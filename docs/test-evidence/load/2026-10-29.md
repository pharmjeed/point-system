## Observations

- **The first evidence run** (`48ba8732`, commit `8a5e224`, 05:07 UTC) measured M1 p95 125 ms, M2 p95 55 ms, 0 errors in
  2000 requests and 100/100 delivered 73.9 s after the first press — with samples that happened to be complete
  (n = 100 and n = 900), which its verdict did not check. A pre-run (`af4efec4`, commit `ecfa053`) measured M1 p95
  155 ms and M2 p95 72 ms; its only failed check was the end-of-run outbox check, which then counted one
  `job.offer_expire` falling due in the second the check ran — the check now uses the system monitor's own rule (due
  longer than `ops.outbox_lag_alert_s`, a lapsed lease, failed or dead). The run above, on the code with the bounded
  database waits, stays far inside the targets (M1 p95 189 ms, M2 p95 91 ms); the differences between runs are within
  the noise of a shared 4-vCPU host.
- **No contention at this load.** With 10 drivers per venue and 20 requests per venue in the minute, every request
  went out as a single offer to the longest-idle available driver and was accepted on its first round
  (`point_dispatch_offers_total{mode="single",outcome="accepted"} 100`, no broadcast, no escalation, no 409/410). The
  average time to claim, 5.1 s, is the virtual drivers' 1–10 s decision time. Parallel accepts, the priority guard and
  next-task reservations are proven by the race suite (`pnpm test:race`, PNT-063), not by this profile.
- **Where the time goes.** A press is acknowledged in 6 ms (p50; the webhook only stores and enqueues), the worker turns
  it into a cycle and an offer within ~10–100 ms, and the realtime publication reaches the 9 other drivers of the pool
  in 49 ms (p50) after the accept's transaction began. No database lock wait was recorded
  (`point_db_lock_wait_seconds_count 0`).
- **Database connections.** The api opened its 20 pooled connections at the burst without lock waits, slot timeouts or
  latency impact; the worker used 9. A bigger deployment sizes `DATABASE_POOL_MAX` per process against the server's
  `max_connections` (05 §7); with the bounded waits a request that cannot get a slot within
  `DATABASE_CONNECT_TIMEOUT_MS` (5 s) answers `503 SERVICE_UNAVAILABLE` with Retry-After instead of waiting.
- **Representativeness.** The machine is a 4-vCPU development host shared with other build jobs (17 §11 asks for
  staging sized like production). Repeat the run there before the pilot and before any expansion (17 §11, Q-08):
  `pnpm ops:load --rate <n>`; the harness creates its own `point_load_*` database and never touches another.
